## Frontend Design Standards

> The UI must look like it was **hand-crafted by a skilled designer** — not generated by AI.

### Visual Identity

- Use a **curated color palette** with HSL-tuned values — avoid raw primary colors (`#ff0000`, `#0000ff`)
- Define all colors, spacing, radii, shadows, and typography as **CSS custom properties** in `common.css`
- Use **Inter** (weights: 400, 500, 700) from Google Fonts — never rely on browser defaults. This is the only external resource allowed (see § Development Constraints)
- Apply **consistent spacing rhythm** — use a base unit (e.g. `0.5rem` increments) for all margins and padding

### Layout & Responsiveness

- Design **mobile-first** — start with single-column layout, then enhance for wider viewports via `min-width` media queries
- Use **CSS Grid or Flexbox** for page-level and section-level layout — never use tables or floats. Absolute/fixed positioning is permitted for overlays, tooltips, dropdowns, and the tilt indicator dot
- All interactive elements must have a **minimum touch target of 44×44px** on mobile
- Check every page at each breakpoint listed in `L1/1requirment.md` § CSS

### Micro-Interactions & Polish

- Add **subtle transitions** (150–300ms `ease-out`) on hover, focus, and state changes — the interface must feel alive
- Buttons must have distinct **hover, active, focus, and disabled** states
- Use **smooth gradients** on primary CTA buttons and **glass-morphism effects** on card containers and modal overlays — avoid flat, lifeless surfaces
- Loading states must use **skeleton screens or animated spinners** — never leave a blank screen while data loads
- Error states must be **visually clear** (color + icon + message) — never show raw error strings or empty containers

### Anti-Patterns (Do Not)

- **Do not** use default browser form styling — all inputs, buttons, and selects must be custom styled
- **Do not** use generic placeholder text like "Lorem ipsum" — use realistic IoT-related labels
- **Do not** hard-code pixel values for font sizes — use `rem` or `em` relative units
- **Do not** leave `:focus` styles as browser defaults — provide visible, accessible focus indicators

## Backend & Security Standards

> The backend integration must be **accurate, resilient, and secure** — following zero-trust and defense-in-depth principles.

### API & Data Handling

- **Validate all API responses** before use — check HTTP status codes, verify expected JSON structure, handle `null`/`undefined` gracefully
- Wrap every `fetch()` and `JSON.parse()` call in **`try...catch`** — never let an unhandled exception crash the UI
- Implement **request timeouts** on all `fetch()` calls using `AbortController` with a 10-second deadline. This does **not** apply to WebSocket connections (see WebSocket Resilience)
- Display **user-friendly error messages** — never expose raw API errors, stack traces, or internal server details to the user

### Authentication & Token Management

- Persist tokens in **`sessionStorage` only** — never in `localStorage`, cookies, or long-lived global variables; read them from `sessionStorage` when a request needs them. Session is tab-scoped by design; closing the tab requires re-login
- Implement **reactive token refresh** — when any other API call returns `401`, attempt **one** silent refresh using the stored `refreshToken`, then retry the original request **once**. If the refresh fails, clear the session and redirect to login. This is the only automatic retry allowed
- **Clear all credentials on logout** — remove tokens, close WebSocket connections, and redirect to login
- Never log tokens, passwords, or secrets to `console.log()` — sanitize all debug output

### WebSocket Resilience

- Implement **Exponential Backoff Reconnect** on WebSocket disconnect — delay 1s, 2s, 4s, ... up to max 30s. A reconnect timeout (10s per attempt) counts as a failed attempt and advances the backoff
- **Clean up resources** on disconnect — call `ws.close()`, clear all event listeners, cancel pending timers via `clearTimeout()`
- Guard against **data inconsistency** — if incoming WebSocket data contains `NaN`, `null`, or values outside expected sensor ranges (see `L1/3api-contract.md` § Sensor Value Ranges), display a fallback state (last known good value or `--`) instead of corrupting the UI

### Security Rules

- **Zero-trust boundary inputs** — validate and sanitize every value received from the server before rendering in DOM
- Never use `innerHTML` with untrusted data — use `textContent` or DOM API methods to prevent XSS
- If the login or token-refresh endpoint itself returns an unexpected status (4xx/5xx), **do not retry** — display a user-friendly error (or redirect to login for a failed refresh) and document the handling strategy in `DECISION.md`

## Development Constraints

- Use only **native browser APIs** — do not install or load external JavaScript/CSS libraries, frameworks, or packages. The only exception is the Inter font from Google Fonts
- **Do not** modify the input files: `Skill.md`, `L1/1requirment.md`, `L1/2builder.md`, `L1/3api-contract.md`. If one looks wrong, ask the developer and record the answer in `CLARIFICATIONS.md`
- Follow the logging and clarification protocols defined in `L1/2builder.md`
- If there is a **security risk**, halt the current task, document it in `DECISION.md` with a severity assessment, and escalate to the developer before proceeding (a **Halt** condition in `L1/2builder.md` § Stop Conditions)
